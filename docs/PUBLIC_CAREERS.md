# Public tenant careers

Account requirements have been updated: browsing stays public, but applying now requires candidate registration, email-code verification, and sign-in. See [Verified candidate accounts](CANDIDATE_REGISTRATION.md) for the current account, API and email configuration. The earlier anonymous intake is retired; existing application receipts remain valid for tracking.

The tenant root `/` (and `/careers`) is the anonymous compact job directory. Location and Job Category filters, keyword search and pagination are stored in the URL. Desktop uses a filter sidebar; mobile collapses filters above the list. Detail routes are `/careers/jobs/{id}` and applications use `/careers/jobs/{id}/apply`. Login remains `/login`. Staff Today moved to `/today`; role-specific homes and all staff API authorization remain protected. Direct/non-portal deployments should set any explicit `STAFF_UI_URL` override to their console's `/today` URL (the new default); public tenant branding requires the registered tenant-host deployment.

`GET /bff/public-tenant` exposes only the active host's tenant ID and display name. The gateway resolves registered active tenants, replaces tenant parameters on public job/consent reads, rejects cross-tenant overrides and platform-host access, strips spoofed tenant headers and binds multipart application intake to its resolved host. No credentials are returned to the public UI. Public requests omit staff cookies.

`GET /api/v1/public/jobs` accepts `page` (1-based, max 100000), `pageSize` (1–50, default 12), `keyword` (max 200), `location` (exact, max 200) and `categoryId` (max 100). Response: `data`, `total`, `page`, `pageSize`, `totalPages`, `locations`, `categories` (`id`, `name`). Search is escaped literal text over title/team/location/description, not a user-supplied regex. Mongo performs filtering/counting/paging and deterministic publication-date/id sorting. Choices cover the full published catalog, independent of current filters/page. No staff metrics are queried or exposed.

Only OPEN jobs whose current version equals a positive approved version are public. Detail projects only candidate-facing fields: title/team/location/level, approved description/skills, category/mode, headcount, salary band and knockout question prompts. Required knockout answers, rubric weights, internal hiring reasons, staff identities and activity are never serialized. Draft, pending, paused and closed jobs return 404.

Authenticated applications reuse CAREER consent, resume processing and receipt tracking via `/api/v1/candidate/applications`. Identity/contact details come from the verified candidate profile, not client-supplied identity fields. Name, email, location and phone are required during registration; resume/processing consent/configured questions are required when applying. Resume must be non-empty PDF/DOC/DOCX up to 10 MB; the server checks extension and file signature before intake. Identical retries retain their receipt; a deterministic candidate/job key also prevents duplicate applications with different client keys. No automatic mutation retry occurs. Only the application receipt is stored in tab-scoped session storage; passwords, personal form values and files are not saved there.

Existing legacy career clients still receive a `data` array; list results are now paginated. Clients that need additional pages must send `page`/`pageSize`. Job categories are immutable approved-version snapshots; missing values on legacy jobs are not invented.

# OpenHire application chart

This chart packages the 18 deployable modules currently present in this repository. The original 19-application plan also names a separate `integrity-worker`, which is not a separate Gradle module here. This chart does not invent an image for it. The discrepancy remains a release-review item.

## Offline validation (no cluster changes)

```sh
helm lint backend/infra/helm/openhire --set image.tag=offline-test
helm template openhire backend/infra/helm/openhire --set image.tag=offline-test
```

For production, pin a tested release, supply registry access and an existing Secret named `<release>-<service>` for each enabled workload. Include the complete service-specific environment configuration: MongoDB URI, Kafka/Redis connections, internal credentials, OIDC issuer/JWK URLs, service URLs, model endpoints and provider secrets as applicable. Use `http://<release>-<service>:8080` for in-cluster service URLs. Neither infrastructure nor secret values are generated by this chart.

The resume processor is disabled by default: provision a suitable persistent volume and scanning/extraction dependencies, then enable it with `existingClaim`. Review whether the storage supports multiple replicas before enabling autoscaling. Mount integration JSON credentials read-only through service `volumes` and `volumeMounts`, and set `INTEGRATION_SECRETS_DIRECTORY`. Enable provider writes only after configuration and security review.

## Per-service image promotion

Each service supports `image.repository`, `image.digest` and optionally `image.tag` under its own `services` entry.
A nonempty digest takes precedence over the tag; omitted overrides retain the global registry/tag behavior.
The global `image.tag` is still required as the fallback for services without an override.

The [GitHub CI/CD pipeline](../../../../.github/README.md) promotes tested images by digest into an existing Helm release,
using `--reuse-values` so other service versions and environment settings are retained. It records `ci.sourceSha`
and rejects incomplete/out-of-order releases. Initial installation, secret synchronization, infrastructure changes
and enabling previously disabled services remain reviewed bootstrap/configuration operations.

The chart includes non-root containers, read-only root filesystems, health probes, graceful shutdown, rolling updates, disruption budgets, optional CPU autoscaling, optional TLS ingress and ingress isolation. It deliberately does not restrict egress: cluster-specific DNS, databases, broker, model server and approved external providers need an explicit reviewed egress policy. Add monitoring namespace access if scraping directly.

Default two-replica settings are intended for a Kubernetes test/production environment, **not** the existing 8 GB Docker Desktop stack. This chart was not deployed. Lint/template checks are not evidence that SLO, failover, storage, rolling upgrade or restore acceptance has passed.

Before release: verify all environment names against each service's application configuration, resource requests against measured load, TLS/issuer/redirect URLs, persistent storage, secret rotation, network policy enforcement, immutable images and rollback compatibility. Do not deploy development credentials or the `offline-test` tag.
